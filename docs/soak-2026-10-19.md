## Problems and plan

Ordered by payoff. P1–P4 all reduce the same cost: the background capture.

### P1: Every background poll walks the whole IORegistry (energy, high)
`LiveMonitor.pollTick()` → `scheduleCapture(urgent: true)` → `RegistryCapture.capture`. This re-reads every port node, USB device, Thunderbolt switch and display every 10 s.
Those topology parts already have IOKit match, interest and display notifications. The poll only exists to refresh power ("keeps the menu bar text fresh").
**Plan:** give poll ticks a power-only capture. Re-read battery, adapter and SMC, and copy the topology fields from the last `RawSnapshot`.
Notification, display, start and `refreshNow` captures stay full. The change lives in `LiveMonitor.runCapture` and a `RegistryCapture.refreshPower(_:)` next to `capture`.
**Check first:** confirm per-port PD watts come only from SMC or from `IOPortFeaturePowerSource`, which already has interest notifications. If they come from a port node property with no notification, keep that read in the power path.
**Test:** extend the `LiveMonitor` scheduling tests so a poll tick does not call the topology readers. Expect about a 5–10× cut in background CPU.
**Shipped** (`monitor/power-only-polls`): `RegistryCapture.refreshPower` re-reads the battery service and SMC and keeps the rest.
Poll ticks and `AppleSmartBattery` interest now ask for power only. A full capture still runs when any other notification, `start`, `refreshNow` or the UI appearing asks for one, and when the last full capture is older than `LiveMonitor.maximumTopologyAge` (60 s). That 60 s floor is the safety net for the per-port PD question above.

### P2: Polling continues with the displays asleep (energy, medium)
Nobody can see the menu bar while the screens sleep, yet captures ran every 10 s all night.
**Plan:** in `PortStore`, observe `NSWorkspace.screensDidSleepNotification` / `screensDidWakeNotification`. Do the same for `sessionDidResignActive` / `sessionDidBecomeActive` (fast user switching).
Stop the poll timer while asleep but keep IOKit notifications, so connect/disconnect events and notifications still fire. Call `refreshNow()` on wake.
This needs one `LiveMonitor.setPollingPaused(_:)` that reuses `updatePollTimer()`.
**Shipped:** `PortStore` observes all four notifications and calls `LiveMonitor.setPollingPaused(_:)`. While paused, there is no poll timer and battery-interest (power-only) requests are dropped. Resuming runs a full capture and restarts the timer.

### P3: The power poll runs when nothing shows power (energy, low)
When `menuBarText` is `.none` or `.devices` and no window or popover is visible, nothing needs power values between notifications.
**Plan:** make `backgroundInterval` optional in `PortStore.monitorConfiguration`, set to nil in those modes, and skip the timer in `updatePollTimer()`.
This doesn't help the default setting (`.power`), which is why it ranks below P2.

### P4: Notification captures don't move the poll clock, and each capture reconnects to powerd (energy, low)
After a battery or power-source notification capture, the poll still fires on its old schedule. That adds ~3,300 captures 2–8 s apart (~15 % extra).
**Plan:** at the end of `runCapture`, re-arm the timer from `lastCaptureTime` using the existing `nextPollDeadline`.
Separately, `PowerReader.adapter()` and `powerSourcesListInternalBattery()` open a new `com.apple.iokit.powerdxpc` connection every capture. Cache both and invalidate on the `com.apple.system.powersources.source` notification that is already registered. That removes the per-poll powerd round-trip and the log spam.
**Shipped:** `runCapture` re-arms the poll timer one interval after every capture. The cache turned out to be unnecessary: a power-only capture skips the IOPS API entirely, so powerd is contacted only on full captures (hardware changes plus at most one a minute). A cache keyed on `kIOPSNotifyPowerSource` would have been wrong anyway, because that notification fires only on an AC/battery switch, not when one of two chargers is unplugged.

### P5: Three leaked `NSXPCConnection` cycles to LNDaemonApplicationInterface (memory, watch)
These are App Intents / LinkServices connections. Bus Stop has no `AppIntent` code, so a framework holds them. Total 19.4 KB.
**Plan:** no code change. Record the count on the next soak. If it grows with window opens, reduce it to a sample and file Feedback.

### P6: The closed topology window keeps its whole view graph (memory, low)
`WindowManager` reuses windows by design (`isReleasedWhenClosed = false`, `topologyWindow` kept). The graph and inspector views stay allocated after close.
They used no CPU in the sample, and the footprint dropped back to 46 MB from the 139.5 MB peak.
**Plan:** no change for now. Revisit only if a memory budget is set. The fix would be dropping `contentViewController` on close and rebuilding it in `showTopology`.

### P7: Unexplained AppKit error, Mon 06:22:34 (reliability, unknown)
One `E` line from `com.apple.AppKit:General` on the main thread, shortly after the popover opened this morning. The text is redacted.
**Plan:** reproduce with the app run from Xcode (private log data visible), opening the popover and then the topology window. Log the text here and decide.

### P8: No app-level telemetry (observability)
Bus Stop logs nothing itself (no `Logger` / `os_log`). Everything above was reconstructed from system XPC lines and `sample`.
**Plan:** add one `Logger(subsystem: "io.github.static74.busstop", category: "monitor")` in `LiveMonitor`. Log capture kind and duration at debug level, and capture notes at error level, plus one signpost around `RegistryCapture.capture`.
The next soak can then read `log show --predicate 'subsystem == "io.github.static74.busstop"'` directly.
**Shipped:** `LiveMonitor` logs each capture's kind and duration (debug), new capture notes (error) and polling pause/resume (info), and signposts `RegistryCapture.capture` and `refreshPower`. `Support/Info.plist` sets `OSLogPreferences` so the debug lines are saved to the log store. Read them with `log show --predicate 'subsystem == "io.github.static74.busstop"' --debug`. A first run showed full captures at ~22 ms and power-only at ~6 ms.
